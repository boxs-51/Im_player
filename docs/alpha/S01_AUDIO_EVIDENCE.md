## Shutdown lifecycle / incomplete playback-state guard — 2026-10-21

The Windows implementation emits `[Lifecycle] phase=STOP component=...` for `PlayerSession`, `AudioOutputWorker`, `AudioProcessor` and `AudioCaptureManager` into the same evidence file as `[AUDIO-TELEMETRY]`. However `LifecycleEvidence::Emit` supplies neither `t_us` nor `load_id`; cross-thread append order is not a reliable proof of exact causal ordering or session identity.

At the RED-first test commit `fac9fb1d59f1c69d412f3b6d5033bee31bbf6a80`, [GitHub S01 run #39585947150](https://github.com/boxs-51/Im_player/actions/runs/39585947150) reproduced exactly **3 FAIL + 4 ERROR, 24/31 PASS** on Ubuntu and Windows without changing the pre-existing 24 tests. These tests establish risks of false attribution after STOP, partial playback state and permissive `--require-reproduction`.

The new analyzer excludes underflow markers logged **after** one of the above STOP records (conservative fail-closed in shared trace), distinguishes `playback_context_verified=true` only when **all five** source-emitted playback flags (`paused`, `core_idle`, `idle_active`, `seeking`, `pause_for_cache`) are explicitly zero, and prefers a later correlated candidate with complete active flags over an earlier weak candidate. Incomplete state may still yield a *marker observation* for legacy investigation, but the output marks `playback_context=UNKNOWN` and the CLI `--require-reproduction` refuses to pass it. Event/marker association is not causality, and these flags/STOP markers are not a trusted user-heard audio oracle.

**Unresolved:** lifecycle STOP has no per-load identity and log append order across threads may race. The conservative STOP handling can produce false negatives for interleaved sessions, but must not be portrayed as a complete physical shutdown classifier. No C++ production instrumentation or host playback was added; PR #62 remains DRAFT, S02 HOLD, exact-media physical Debug/Release NOT_RUN.

## Lifecycle STOP epoch isolation and identity audit (2026-10-21)

Native `LifecycleEvidence::Emit` serializes `phase/component/id/pid/tid` but does **not** serialize `load_id` or a monotonic `t_us`. `PlayerSession.id` is an application-defined string; audio worker identities are pointer strings; SDL telemetry carries numeric `load_id` and generation. Their values must **not** be joined by guessing. Distinct mutexes also mean inter-thread append order is not a strict causal ordering guarantee.

**RED-first GitHub-only proof:** test-only `50077fe0653e56df00d953835cbf57ca3c650df1` added five immutable test cases at `tests/test_issue42_lifecycle_identity.py`, and a workflow trigger without changing analyzer source. [S01 RED run #39591312100](https://github.com/boxs-51/Im_player/actions/runs/39591312100) on both Ubuntu and Windows: **36 total, 2 FAIL + 2 ERROR, 32 PASS**. Two false attributions were reproducible: an underflow preceding STOP improperly borrowed a capture publication recorded after STOP, and it borrowed a later pipe-disconnect stage whose supplied `t_us` was earlier than the underflow. Two missing-key errors required explicit identity uncertainty output. The complete preexisting 31-test suite remained PASS.

The minimal correction increments a diagnostic lifecycle epoch whenever a STOP is logged for `PlayerSession`, `AudioOutputWorker`, `AudioProcessor` or `AudioCaptureManager`. All telemetry events are tagged with this epoch and comparisons require *the same load_id and the same log segment*. An underflow logged after STOP remains fail-closed even if a later START appears. JSON now reports `lifecycle_stop_count` and `lifecycle_identity_binding=UNVERIFIED` when such STOPs exist; `NO_STOP_OBSERVED` otherwise. These diagnostics are not identity attestations and do not unlock physical reproduction acceptance.

**Conservative limitation:** unrelated sessions may share the same log and lifecycle IDs are not bound to PCM load IDs. A STOP could cause false negatives; log ordering across independent emitters cannot prove physical shutdown/clock order. The correct long-term fix requires an explicitly approved native instrumentation contract adding trusted session/load/timestamp correlation. No native C++ change, physical audio playback, merge or S02 opening was performed here.

## Native continuity marker parity — 2026-10-21

Source audit found two **unscoped real native producers**:
- `AudioCaptureManager.cpp` emits `[AUDIO-TELEMETRY] CONTINUITY stage=PIPE_DISCONNECTED t_us=... connection_index=... reason=... running=...` **without** `load_id`.
- `AudioOutputWorker.cpp` emits `[AUDIO-TELEMETRY] CONTINUITY stage=OUTPUT_DEVICE_OFFLINE_DROP t_us=... sequence=... generation=... reason=device_unavailable` **without** `load_id`.

Prior synthetic tests used `load_id` on these stages; such an attribution was **not demonstrated with genuine source-emitted records**. RED-first test-only `cf57c58a30af4e046edd01abf43138a786bbd4d9` added four producer-shape contract cases; [S01 RED #39593202401](https://github.com/boxs-51/Im_player/actions/runs/39593202401) on **Ubuntu and Windows** produced **40 tests, 4 ERROR, 36 PASS** (missing `unscoped_marker_counts`), with all existing tests unchanged.

The analyzer now always exposes `unscoped_marker_counts` for both stages and adds `unscoped_pipe_disconnect_observed` / `unscoped_output_offline_drop_observed` evidence when the stage is near an underflow in the *same conservative lifecycle log segment*. These are **unbound observations only**: they must not change `classification=INCONCLUSIVE` to a cause, grant `--require-reproduction`, or assert a load identity. A true per-load classification would need independently approved native instrumentation with a trustworthy `load_id`, timebase and session binding, plus physical playback validation. No C++ source was modified.
